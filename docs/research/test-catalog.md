# Haddon Upstream Behavior and Test Catalog

**Established:** 2026-08-13  
**Roadmap ticket:** HADDON-050  
**Scope:** Behaviors worth specifying independently from the vendored e-reader sources

This is the maintained compatibility backlog for Haddon. It translates upstream tests, fixtures, and implementation edge cases into observable promises. It does not imply that Haddon will copy upstream code or ship upstream fixtures.

## How to use this catalog

- IDs are stable. Keep an ID when a behavior moves between tickets or priorities; mark retired rows instead of renumbering them.
- `Haddon ticket / status` describes implementation status, not whether the upstream evidence exists. `Queued` means Haddon does not yet enforce the promise.
- Each Haddon test should cite its catalog ID and use project-owned inputs unless the row explicitly permits an adapted fixture.
- Exact paths refer to the vendored subtree snapshots recorded in [gems-ledger.md](gems-ledger.md). Revalidate line ranges when a subtree is updated.
- A W3C publication often requires human visual or interaction judgment. Do not label it automated until a Haddon harness has a machine-observable oracle.
- A visual case is not a unit test. Record browser, viewport, fonts, pixel tolerance, and artifacts when HADDON-052 implements it.
- GPL/AGPL evidence is behavior-only: specify and implement from first principles. MIT/BSD code still needs a bounded reuse review. W3C fixtures need the applicable notice and per-asset review.

Test-form labels:

- **Unit:** deterministic in-process assertion over a small Haddon-owned input.
- **Fixture/automated:** packaged EPUB or resource fixture with a machine-observable result.
- **W3C/manual:** upstream conformance publication whose current oracle is visual or interactive.
- **Browser integration:** automated browser behavior, DOM, event, or accessibility-tree assertion.
- **Visual:** screenshot comparison under a pinned environment.
- **Fuzz/property:** generated inputs or algebraic laws with stored regressions.
- **Benchmark:** repeatable timing or memory measurement, not a pass/fail correctness test by itself.

## First implementation cut

The first CI change should not attempt all P0 rows at once. Start with these 15 executable contracts:

1. TC-001 through TC-008 for locator serialization, CFI laws, and quote recovery.
2. TC-009 through TC-014 for resource containment and range semantics.
3. TC-018 for reading order.

Then convert the awkward EPUB from HADDON-010 into the shared fixture for TC-019 through TC-028. TC-015 through TC-017 and TC-030 need the resource/security and browser harnesses; keep their W3C originals manual until those oracles exist.

## Maintenance checklist

When implementing or updating a row:

1. Link the Haddon test file and change its status to `implemented` or `partial`.
2. Record any intentional divergence from upstream behavior in the test name or adjacent design document.
3. If adapting upstream bytes, add the exact asset review and required notice to [gems-ledger.md](gems-ledger.md).
4. Run the smallest relevant unit/fixture/browser suite and record deterministic environment details for visual or performance artifacts.
5. After a subtree update, verify every cited path/range in this document before accepting upstream changes.
